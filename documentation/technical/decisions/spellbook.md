# Technical Specification: Spellbook

- **Status:** Accepted
- **Date:** 2026-11-12
- **Functional spec:** `documentation/specifications/features/SPELLBOOK.md`
- **Related docs:** `AGENTS.md`, `documentation/technical/TESTING.md`, `documentation/technical/INVARIANTS.md`, `documentation/technical/decisions/TECHNICAL_SPEC_TEMPLATE.md`

## 1. Context & Scope

- **Goal / user-visible behavior:** Enable users to build and manage multiple spellbooks (spell-ID collections) alongside the spell list: create/rename/delete/duplicate/switch spellbooks, add spells (individual or all filtered) into sections with defined dedupe/placement rules, manage sections and spell ordering/movement, persist locally, export/import a spellbook as JSON, and export a read-only printable PDF (Paged.js + browser print dialog) with searchable text and good-enough cross-browser visual/layout parity. Navigation uses explicit History routes with deep-linkable spellbook views.
- **In scope:** Per `SPELLBOOK.md` — routing/view model for spell list and spellbook screens (`/spelllist`, `/spellbooks`, `/spellbooks/:id`, `/spellbooks/:id/print`), spellbook domain/state and local persistence, section/spell CRUD and ordering/movement semantics, add-from-list flows (including create-on-add), JSON export/import with validation and error handling, PDF export (read-only, Paged.js pagination, searchable), “Clear filters” control and list-filter preservation/restoration across navigation, and required automated test coverage for contracts/risks.
- **Out of scope / non-goals:** Per-spell notes/custom text edits, URL-encoded spellbook content, combined JSON+PDF export, pixel-perfect web/PDF pagination parity, drag-and-drop ordering, file-upload import UX beyond JSON payload handling, navigating from spellbook entry back to spell details, “clear spellbook” action (duplicate exists), and any backend/server persistence. Full spellbook data must never be encoded in the URL.
- **Constraints:** Client-only Vite + TypeScript + Alpine app (no backend). Existing list filtering/sorting/columns and URL search-param sync must continue to work on `/spelllist`. History API routing requires SPA fallback and correct asset/base handling in dev/build/preview (base may be `/` or `/AnimaSpellBook/`). PDF export must use browser print dialog, be searchable (real text), and target at least Chromium and Firefox using Paged.js (no browser-specific solution where possible). No partial/corrupt state on invalid persistence/import (INV-IMPORT-NO-PARTIAL, INV-PERSISTENCE-ROUNDTRIP). Single-writer invariants for URL and route↔view (INV-URL-SINGLE-WRITER, INV-ROUTE-RENDER).
- **Assumptions:** Spell dataset is bundled/static and identified by unique `id`. `localStorage` is available (quota/serialization failures possible and must be handled safely). Users share spellbooks via exported JSON payloads (not URLs/localStorage). Browser “Save as PDF” from Paged.js-paginated HTML preserves selectable/searchable text in Chromium and Firefox (validation spike). Existing Alpine/reactive patterns and test setup (Vitest jsdom + Playwright e2e) remain baseline.
- **Unknowns / open questions:** Exact UI composition/copy for add/move/target-selection prompts (must satisfy functional behaviors). Final localStorage key and payload field naming (versioned, consistent). Performance envelope for very large spellbooks with Paged.js pagination. Exact default-name increment details (persisted counter recommended). Any deployment environment specifics beyond Vite dev/preview must be confirmed to support SPA fallback for deep links.

## 2. Decisions (ADR-style)

### D1. Routing model and URL ownership

- **Status:** Accepted
- **Context / problem:** The feature adds multiple primary screens and deep-linkable spellbooks; current `URLSync` writes `replaceState(pathname?+search)` on every store change, conflicting with path-based routing. INV-URL-SINGLE-WRITER and INV-ROUTE-RENDER require a single URL/history owner and reliable route→rendered-view, including deep-link/refresh on nested routes.
- **Options considered:** A) History routes with a dedicated router as sole URL writer (`/spelllist`, `/spellbooks`, `/spellbooks/:id`, `/spellbooks/:id/print`) — future-proof, explicit; requires SPA fallback/base/E2E. B) Hash routes — explicit/deep-linkable without server fallback but less preferred for future URL growth. C) Split writers (router for path, store/URLSync for query) — smaller refactor but high clobber/loop and invariant risk.
- **Decision:** Adopt History routes with a dedicated router module as the single URL/history writer. Routes: `/` → redirect `/spelllist` (preserve query); `/spelllist` list view (filter/search/sort/cols params owned here only); `/spellbooks` management/selector+create (empty-friendly); `/spellbooks/:id` editable active spellbook; `/spellbooks/:id/print` deep-linkable read-only print/export. Unknown/missing `/spellbooks/:id` or `/print` → redirect `/spelllist`. List params preserved across navigation and restored on return to `/spelllist`; “Clear filters” resets defaults via router. `URLSync` removed/refactored so no direct history writes remain.
- **Rationale:** Explicit, future-proof URLs requested; single router writer prevents URL/view races and makes route contracts testable. Deep-linkable print route aligns with explicit routing and E2E/refresh coverage.
- **Consequences / tradeoffs:** Refactor of current URL sync and app shell/view rendering. SPA fallback and asset/base correctness (nested routes, `/` vs `/AnimaSpellBook/`) become required with automated E2E coverage. Router must coordinate with stores without introducing multiple writers.

### D2. State/store architecture and ownership

- **Status:** Accepted
- **Context / problem:** Spellbooks add a large independent domain (multi-book CRUD, sections/order/move, active selection, persistence, import/export) distinct from spell catalog and list filtering/sorting/columns.
- **Options considered:** A) Separate `SpellbookStore` (spellbook domain + persistence, single writer) and keep `SpellStore` for catalog/list state — clear boundaries, testable; needs new contracts. B) Extend `SpellStore` with spellbook responsibilities — fewer modules but mixed concerns/god-store and weaker boundaries.
- **Decision:** Introduce separate `SpellbookStore` (Alpine-reactive) as single writer for spellbook collection, active spellbook id, mutations (create/rename/delete/duplicate, add spells, section create/rename/delete/reorder/clear, spell reorder/move/bulk-move, dedupe/placement), localStorage persistence, and JSON import/export/validation. `SpellStore` keeps spell loading and list filter/search/sort/column behavior. Router coordinates route↔active spellbook id and list-param preservation/restoration. Stores do not write URL/history.
- **Rationale:** Clear separation of concerns and single writer per concern; domain logic becomes unit-testable independent of routing/UI and supports future growth.
- **Consequences / tradeoffs:** Requires well-defined store APIs/events and coordination points (router↔stores, add-from-list uses catalog snapshot + spellbook mutation) while avoiding cross-store hidden coupling.

### D3. Routing ↔ spellbook view behavior

- **Status:** Accepted
- **Context / problem:** Active/editable semantics, management, and delete/navigation must be explicit and consistent for History routes and updated functional spec.
- **Options considered:** A) Explicit management vs editable routes with defined transitions (chosen): `/spellbooks` always reachable/empty-friendly for management+create; `/spellbooks/:id` editable active view; defined create/select/delete/unknown transitions. B) Redirect `/spellbooks` when empty or auto-pick random book on delete-active — rejected as inconsistent with confirmed behavior.
- **Decision:** `/spellbooks` always reachable (empty state + create). `/spellbooks/:id` is editable view and navigating to it sets it active; `/spellbooks` is non-editing management. Selecting navigates to `/spellbooks/:id` and activates; creating from `/spellbooks` creates, activates, navigates to `/spellbooks/:newId`. Deleting the active spellbook always navigates to `/spellbooks` (empty if none remain). Unknown/missing `/spellbooks/:id` or `/spellbooks/:id/print` redirects to `/spelllist`. Print route is deep-linkable/refreshable and read-only.
- **Rationale:** Predictable delete landing, explicit management page, and stable deep links matching confirmed UX; avoids surprising auto-switch to a random book.
- **Consequences / tradeoffs:** Differs from original spec text (updated). Route guards/redirects must be centralized in the router to remain single-writer and consistent.

### D4. Persistence, data model, and validation boundaries

- **Status:** Accepted
- **Context / problem:** Multiple spellbooks, sections, ordering, import/export, and auto-save/restore require a durable, validatable schema and safe load/save behavior (INV-PERSISTENCE-ROUNDTRIP, INV-IMPORT-NO-PARTIAL).
- **Options considered:** A) Single versioned localStorage envelope with uniform ordered sections, explicit `name:null` default section, stable IDs, runtime parse/validate at boundaries — clear/testable/migratable. B) Ad-hoc/minimal shape (implicit default) — more branching, harder validation/migration and ordering correctness.
- **Decision:** Single versioned localStorage key (e.g. `anima-spellbooks`) envelope `{ version: 1, activeSpellbookId, nextSpellbookNumber, spellbooks[] }`. Spellbook `{ id(uuid), name, sections[] }`. Section `{ id(uuid), name: string|null, spellIds: string[] }` ordered; `name:null` = default unnamed section. Persist `nextSpellbookNumber` for default naming stability. Runtime parse/validate on restore and import at untrusted boundaries (typed result or clear error, no partial/corrupt state); save only validated state; handle read/write/parse failures safely. User-facing position edits are 1-based and clamped to valid range.
- **Rationale:** Uniform model simplifies §5–§6 rules and makes round-trip/import validation deterministic; explicit version enables migration.
- **Consequences / tradeoffs:** Requires schema/types and validators and future migration handling. In-memory and persisted shapes must stay consistent.

### D5. JSON export/import contract

- **Status:** Accepted
- **Context / problem:** §8.2 requires canonical single-spellbook export/import, overwrite-or-create choice, strict invalid-payload rejection, and skipping unknown spell IDs with summary — all without partial/corrupt state.
- **Options considered:** A) Versioned single-book payload with stable route-friendly overwrite and regenerated internal IDs where safe — clear validation and collision avoidance. B) Export/import stored objects with all internal IDs verbatim — route/ID conflicts on overwrite/create and collision risk.
- **Decision:** Versioned, self-contained single-spellbook payload (includes version/kind, spellbook id/name, sections with name+spellIds/order; UUIDs carried as content metadata). **Overwrite active:** replace active book content (name/sections/spell refs) but keep active book UUID (stable route); regenerate section IDs on import; apply atomically after validation. **Create new:** mint new book UUID and new section IDs, keep imported name as-is (no uniqueness), ignore imported book UUID. Unknown spell IDs skipped with summary, remaining valid content applied; import normalization enforces per-section uniqueness/valid shape. Invalid payload (structure/type/version/semantic) → clear error and no state changes.
- **Rationale:** Preserves route stability on overwrite (better UX), avoids ID collisions, and upholds validation/atomicity invariants with clear user feedback.
- **Consequences / tradeoffs:** Payload UUIDs not all preserved at runtime (documented). Import must report skipped IDs clearly and round-trip valid content predictably.

### D6. PDF export via Paged.js (read-only, searchable, cross-browser)

- **Status:** Accepted
- **Context / problem:** Spec requires read-only PDF export (no edit controls) via browser print dialog, searchable/selectable text, good-enough visual/layout parity across Chromium and Firefox, A4 portrait 2-column flow with splitting/header/footer rules, and consistent pagination without pixel-perfect parity. Native browser pagination varies.
- **Options considered:** A) Paged.js + dedicated read-only print route/view — client-side pagination for cross-browser consistency with real HTML text (searchable); dependency + render step + spike needed. B) Plain CSS print (`@page`, break hints) — no dependency but pagination differs across engines. C) Client-side PDF library — more control but parallel layout/drift/dependency; raster output not searchable.
- **Decision:** Implement PDF export as dedicated, deep-linkable read-only route `/spellbooks/:id/print` rendering spellbook content (same data/order, equivalent styling intent, no edit controls) using Paged.js for A4 paginated output. User exports via browser print dialog (Save as PDF). Output must remain real/selectable/searchable text in Chromium and Firefox. Add `pagedjs` dependency (pinned). Supported browsers for export behavior: at least Chromium and Firefox.
- **Rationale:** Addresses cross-browser pagination consistency while preserving searchable HTML text; dedicated route isolates export concerns and is deep-linkable/refreshable/testable within SPA/routing model.
- **Consequences / tradeoffs:** Adds dependency and runtime pagination work; must ensure print/save preserves text selectability/search. Performance and complex 2-column break behavior are validation spikes. Print route must satisfy SPA fallback/base-path rules like other nested routes.

### D7. Add/move/management interaction contracts (domain-enforced)

- **Status:** Accepted
- **Context / problem:** Add, targeting, deduplication, section placement, ordering, movement, and delete behaviors have specific functional rules affecting integrity and UX; UI must implement them consistently.
- **Options considered:** A) Implement spec rules as domain operations in `SpellbookStore` with UI prompts/controls bound to them — centralizes invariants and testability. B) Ad-hoc UI-driven mutations — easier to violate rules and harder to test.
- **Decision:** Encode as explicit store/domain operations and UI contracts: add-individual and add-all-displayed (snapshot current filtered/displayed order, append to end of target section, skip duplicates in target); target-section selection or create-new (placement first/last/specific 1-based, clamped); create-spellbook-on-add when none exists; section create/rename/delete/reorder/clear with default↔named conversion and non-last delete choice (delete spells vs move to chosen existing section); spell reorder within section (up/down and 1-based position edit, clamped); move single/bulk to another/new section appended to end of target. UI collects intent via appropriate controls/prompts; domain enforces final validity.
- **Rationale:** Keeps behavioral rules testable at domain/integration layers and prevents UI-only enforcement gaps; aligns with acceptance behaviors.
- **Consequences / tradeoffs:** Richer store API; requires thorough unit/integration tests for rules and edge cases (empty sections, conversions, duplicate prevention, snapshot immutability).

## 3. Technical Design & Contracts

- **State ownership & reactivity/binding model:** `SpellStore` (existing, narrowed) owns spell dataset and list UI state (`spells`, `filteredSpells`, `filters`, `searchQuery`, `sort`, `columns`) and list-param serialization inputs; Alpine-reactive. `SpellbookStore` (new) owns spellbooks, active id, persisted envelope, and all spellbook mutations/import/export/persistence; Alpine-reactive. Router (`src/router/*`) owns route state (`view`, `spellbookId`, print mode) and all history interactions, exposing reactive route info the UI tracks. App shell/view renders from router route state + store state; no ad-hoc view state bypassing router.
- **Single writer per concern:** URL/history — router only (`pushState/replaceState/popstate/redirects`). Route/view resolution — router source of truth. Spell list state — `SpellStore` only. Spellbook domain/persistence — `SpellbookStore` only (active id changes via defined API, localStorage read/write). Spellbook content never in URL (only `:id`).
- **Separation of concerns & responsibilities:** Domain/model (`SpellbookStore`, schema/validation/persistence helpers) handles shapes, invariants, mutations, parse/validate/normalize, round-trip — no DOM/routing. Router handles path parsing/matching, redirects/guards, history, route↔store coordination — no spellbook business rules beyond resolution/activation/navigation. UI components/views render state, collect intent, invoke APIs, show errors/summaries — no direct localStorage/URL mutation. Print/export view is read-only rendering from spellbook data. Utilities provide pure serialization/validation/ordering helpers where appropriate.
- **Module boundaries, data flow & dependency direction:** Router↔stores coordinated at app composition (`main.ts`/app shell) to avoid circular ownership (prefer router depending on store interfaces/callbacks or orchestrator; stores do not write history). `SpellbookStore` depends on schema/validation/persistence helpers and explicit read-only spell-catalog lookup for import/dedupe checks. `SpellStore` remains independent of spellbook domain except UI-invoked integration (e.g. add-all passes displayed spell ID snapshot). Data flow: user action → UI → store mutation → reactive update → render (+ safe persistence side-effect). Route change → router updates route state → view/store sync → render.
- **Interfaces / contracts affected:** Routes/URLs `/`, `/spelllist`, `/spellbooks`, `/spellbooks/:id`, `/spellbooks/:id/print` (+ search params on `/spelllist` only, preserved/restored). Persistence: versioned localStorage envelope for spellbooks + active id + name counter. JSON import/export: versioned single-spellbook schema. Store APIs: new `SpellbookStore`; `SpellStore` gains clear-filters/reset and router-coordination hooks without history writes. UI: list add controls, target/section prompts, clear-filters, spellbook management/editable/print views, navigation.
- **Boundary contracts & validation:** URL/route params ↔ router (untrusted): parse/validate path/`:id` and `/spelllist` search params; unknown/invalid routes or ids → defined redirects with no corrupt state (typed route result). Route/path params ↔ view/state: router exposes typed route state; active spellbook resolved/validated against `SpellbookStore` (missing → redirect). localStorage ↔ domain (untrusted): on load JSON.parse + runtime schema validation (shape/version/types/fields/integrity) → typed state or safe failure with no partial state; on save serialize validated state only. JSON import/export ↔ domain (untrusted): parse + runtime validation (version/kind/structure); invalid → clear error, no changes; valid → normalize/sanitize (regenerate IDs per D5, skip unknown spell IDs with summary, enforce no intra-section duplicates/valid rules) and apply atomically (overwrite keeps active UUID or create-new). Internal module/store interfaces are trusted typed TS; no runtime validation except at untrusted boundaries. Round-trips (`save/load`, `export/import`) preserve valid content/order (modulo regenerated internal IDs per contract); error paths never mutate existing valid state.
- **Code quality & maintainability:** Domain rules in pure/testable functions or store methods (no DOM). Explicit types/schemas for persisted/imported data. Minimize coupling and avoid duplicated serialization/validation logic. Reuse `SpellStore` snapshot for add-all-displayed. Isolate Paged.js/print CSS to print route/view. Centralize route table/guards for future routes.
- **Serving / build considerations:** Vite dev server and preview/build must SPA-fallback `index.html` for deep-link/refresh of all routes (including nested `/spellbooks/:id`, `/spellbooks/:id/print`). `base` is `/` or `/AnimaSpellBook/` (`GITHUB_PAGES`) — router links/redirects, assets, and Paged.js loading must work under both (validation spike). Ensure Paged.js bundled/loaded reliably in dev and production for print view.

## 4. Risks & Mitigations

| Risk | Impact | Mitigation / owner | Residual risk |
|---|---|---|---|
| URL/history multiple writers during router refactor break filters, back/forward, or view rendering (INV-URL-SINGLE-WRITER, INV-ROUTE-RENDER) | High: broken navigation, stale/wrong view, lost filter state | Router as sole writer; remove/refactor `URLSync` history writes; centralize redirects/guards; integration + E2E for route↔view↔URL and popstate/deep-link/refresh | Medium until covered |
| SPA fallback/base-path issues on nested routes in dev/preview/build (`/` vs `/AnimaSpellBook/`) | High: deep-link/refresh 404s or broken assets | Early spike; configure Vite/preview fallback; verify asset/base handling; E2E deep-link/refresh in relevant contexts | Low–Medium (deploy-dependent) |
| Paged.js output non-searchable, incorrect, or inconsistent across Chromium/Firefox (2-col flow, breaks, headers/footers) | High: export unusable or violates spec | Spike (searchable Save-as-PDF, column/break rules, headers/page numbers, performance); dedicated print route; automated checks where feasible + documented verification | Medium |
| Invalid/corrupt localStorage or import payload causes partial state, data loss, or crashes (INV-PERSISTENCE-ROUNDTRIP, INV-IMPORT-NO-PARTIAL) | High: user data corruption/loss | Runtime schema validation at boundaries; atomic apply; reject invalid with no mutation; skip unknown spell IDs with summary only after validation; unit/integration tests | Low if comprehensive |
| Domain rule bugs (dedupe, section conversion/delete, ordering/clamp, move-to-end, snapshot, create-on-add) | Medium–High: incorrect spellbook content/order | Implement rules in `SpellbookStore` domain operations; thorough unit tests per rule and integration tests for flows | Low–Medium |
| Route↔active-spellbook desync (stale/missing id, transitions) | Medium: wrong book shown/edited | Router/store coordination with defined transitions (D3); resolve/validate ids; redirect unknown to `/spelllist`; transition tests | Low–Medium |
| Filter preservation/restoration across navigation regresses list behavior | Medium: lost/confusing filters or broken shareable `/spelllist` URLs | Explicit preserve/restore contract; params only on `/spelllist`; Clear filters control; regression integration/E2E | Low with coverage |
| Performance/memory issues for large spellbooks (rendering, Paged.js) | Medium: slow export/UI | Spike with representative large data; avoid unnecessary re-renders; paginate only in print view | Medium (data-dependent) |
| localStorage quota/write failures | Low–Medium: changes not persisted | Catch/handle safely (no crash/corruption), surface user-visible error where appropriate; keep in-memory state consistent | Low |

## 8. Reviewer Guidelines (for `/assess`)

- **Contracts to uphold:** Router is the sole URL/history writer (INV-URL-SINGLE-WRITER); route changes must drive correct rendered view/state (INV-ROUTE-RENDER). `SpellbookStore` sole writer for spellbook domain/persistence; `SpellStore` sole writer for list state. Routes/redirects follow D1/D3 (`/spellbooks` empty-friendly, unknown ids → `/spelllist`, delete-active → `/spellbooks`, print route read-only/deep-linkable). No spellbook content in URLs.
- **Boundary validation to uphold:** Typed route/param parsing and validation at URL boundary; runtime schema parse/validate at localStorage restore and JSON import boundaries with typed results or clear errors and no partial/corrupt state (INV-PERSISTENCE-ROUNDTRIP, INV-IMPORT-NO-PARTIAL). Import normalization (ID regeneration per D5, unknown spell IDs skipped with summary, dedupe/shape rules) applied atomically. No unsafe raw persisted/imported data used internally.
- **Cross-cutting invariants to uphold:** Applicable `documentation/technical/INVARIANTS.md` items (INV-URL-SINGLE-WRITER, INV-ROUTE-RENDER, INV-PERSISTENCE-ROUNDTRIP, INV-IMPORT-NO-PARTIAL) implemented as cheap guards at owners and exercised by tests/runs.
- **Feature-specific invariants to uphold:** Section 6 items (no intra-section duplicate spell IDs; spellbook/route identity consistency; list params scoped/restorable) enforced at owners and exercised by tests/runs.
- **Design/quality to uphold:** Clear separation of concerns (router vs stores vs views), high cohesion/low coupling, explicit dependencies, domain rules testable without DOM, simplicity/maintainability per spec. Avoid regressions to existing list/filter/URL behavior.
- **Test adequacy expectations:** Required layers/coverage per sections 5–7 and `documentation/technical/TESTING.md`. Integration/UI-binding and E2E for routing↔rendered view, URL↔UI↔results, deep-link/refresh and SPA fallback/asset-base on nested routes, and key user flows (add/manage/move/import/export). Boundary parse/validate/round-trip/error/no-partial-state cases covered. Cross-browser (Chromium, Firefox) PDF/searchability/pagination behavior validated per spikes and feasible automation. Missing automated coverage for affected user-visible/routing/serving behavior is blocking.
- **High-risk areas / focus:** Router/URL single-writer refactor and `URLSync` removal; deep-link/refresh + base path for nested/print routes; `SpellbookStore` domain rules (sections, ordering, dedupe, snapshot, move) and state transitions; persistence/import validation and atomicity; Paged.js print view (read-only, searchable text, 2-col/breaks, headers/footers/page numbers).
